feature/timeline-statistics 사전 검토 및 변경 결과 (2026-11-26)

1. 작업 기준과 분리
GitHub 최신 feature/timeline-statistics: 14db634
비교 대상 GitHub feature/generation-timeline: 4579b45
새 디렉토리: outputs/Life-Game-timeline-statistics
기존 outputs/Life-Game-timeline의 파일은 수정하지 않는다.
GitHub의 timeline-statistics는 4579b45에서 통계 기능을 추가한 후속 커밋이다.
이전 로컬 전용 연속 저장/확대 탐색 변경은 원격 기준에 포함되지 않았으므로 이번에 적용했다.

2. 본격 수정 전 검토
기존 timeline 테스트 153개가 통합 브랜치에 변경 없이 포함되어 있음을 diff로 확인.
통계 테스트 6개를 더해 원격 코드 그대로 159개 실행/전부 통과.
원본 로그: integration-baseline-tests.txt

검토한 핵심 동작:
- 초기 0세대, 저장 한도/만료 후 절대 세대 번호 유지.
- 슬라이더/번호/간격/처음/최신 이동 및 잘못된 입력 거부.
- 과거 탐색만으로 미래 기록을 삭제하지 않음.
- 편집한 세대 교체, 이후 삭제, 저장 끝에서 새 계산.
- 편집된 10세대와 새 11~25세대를 다시 재생할 때 기록 유지.
- 안정 상태의 세대 정지와 반복 감지, 편집 전 기록의 반복 비교 제외.
- 기존 파일 형식, 복원 후 격자 경계 계산, 실제 Swing 타이머 연동.
위 자동 검사와 코드 검토 범위에서 timeline 기능 소실을 발견하지 못했다.
실제 OS 창의 메뉴/마우스/파일 선택기 전체를 검사했다는 뜻은 아니다.

통계 연결에서 바뀐 부분:
- 기록 단위를 BoardSnapshot에서 GenerationStatistics로 확장. 내부에 기존 Memento 보존.
- cycleSearchStart의 역할을 통계의 segmentStart로 대체.
- 조회 전용 GenerationHistory.at() 추가. 조회는 현재 커서를 바꾸지 않음.
- Universe의 크기를 너비/높이 중 작은 값에 맞춰 오른쪽 통계 패널 공간 확보.
- StatisticsPanel은 동일한 LifeHistory를 구독하므로 별도 세대 진행 엔진이 없음.
- 원격 버전은 반복 후 실시간 통계를 별도 120개 창에 저장했음.
  이 부분은 새 연속 저장 정책에서 필요 없어져 제거했다.

3. 이번 요청 반영
1) 반복 감지 보존 + 반복 중에도 매 세대 연속 저장: 완료.
   기록을 원형 배열에 저장하여 추가/만료/조회 O(1), 과거 분기 폐기 O(폐기 개수).
   반복 정보는 분석/표시 목적이며 저장 중단 조건이 아니다.
2) 반복 담당 모듈/색상: 검토만 수행. 기존 LifeHistory와 CycleDetector 담당 유지.
   공통 분석 서비스가 timeline/statistics에 결과 제공하는 구조를 장기적으로 추천.
   실제 주기 시작 세대와 감지 세대는 다르므로, 색상을 추가한다면
   먼저 '감지 시점' 표식으로 의미를 제한하는 것을 추천. 미확정 색상/모듈 이동은 미구현.
3) 전체 타임라인 아래 확대 탐색 슬라이더: 완료.
4) 실행/정지 버튼 통합 및 Clock 상태 동기화: 완료.
5) 원격 통합 브랜치의 timeline 보존 여부 사전 검토: 위 159개 및 코드 비교 완료.
6) 기본 저장 한도 100000개: 완료. 실제 기본 생성자로 100005세대 진행/만료/편집 테스트.
7) 시작/끝 세대 직접 지정: 완료. '< 구간', '현재 중심', '구간 >' 버튼 제거.

확대 범위 정책:
- 처음 열 때 현재 세대 주변 최대 100세대 폭을 제안.
- 입력 후 적용 또는 Enter. 저장 범위 안의 정수이며 시작 <= 끝이어야 함.
- 적용은 범위만 바꾸며 보드/현재 세대를 이동하거나 편집하지 않음.
- 사용자 범위는 과거 탐색 및 접기/다시 열기에도 유지.
- 현재가 범위 밖이면 '확대 범위 밖' 표시. 슬라이더를 조작하면 그 범위로 이동.
- 만료/과거 편집으로 기록이 사라지면 범위를 남은 기록 안으로 조정.
- 입력 중에는 다른 상태 갱신이 입력 중인 문자열을 덮어쓰지 않음.
- 1세대만 지정한 경우 슬라이더를 비활성화. 200세대 초과 범위는 과도한 눈금 생략.

4. 현재 검증
전체 193개 통과(153 기존 기능 + 6 통계 + 8 한도 편집 + 10 연속 저장/확대/버튼 + 16 추가 통합 검사).
이전 '반복 후 저장 중단' 기대값은 명시적으로 변경된 요구에 따라 갱신했다.
1000개 경계 테스트는 작은 용량을 명시해 유지하고, 앱 기본 10만 개는 별도로 검증했다.
추가 16개: 잘못된 범위 입력 12종, 사용자 범위 유지, 만료/편집 범위 조정,
입력 중 갱신/넓은 범위/단일 범위, 10만 개 실제 Life 기록과 통계의 편집·재생.
현재 결과: integrated-test-results.txt

5. 메모리/성능 재측정
통계가 없는 이전 폴더의 수치를 그대로 적용하지 않고 이 브랜치로 재측정했다.
64x64 기준 스냅샷 576바이트 + GenerationStatistics 56바이트 + 배열 참조 4바이트.
비반복 10만 세대의 보관 데이터 약 60.65MiB. 객체 크기는 현재 JVM 기준이다.
128MiB 힙 제한의 합성 비반복 모델에서 10만 개 채운 후 GC 후 힙 약 63.24MiB.
같은 시험의 10000회 계산+통계+두 UI 값 갱신 p95 0.0617ms, 최대 29.5621ms,
GC 누적 38ms. 순간 정지가 전혀 없다는 결과가 아니다.
실제 64x64 Blinker 10만 개에서 10000회 진행 p95 0.0935ms, 최대 1.2522ms.
두 화면의 오프스크린 그리기 p95 4.9630ms, 최대 27.7349ms.
반복 상태의 봉인된 스냅샷은 공유하되 모든 세대 통계/번호는 별도 기록한다.
최악 예산은 스냅샷 공유가 없는 비반복 사례로 계산한다.

4GiB RAM 예산 가정: OS/백그라운드 2048MiB + 다른 앱 1024MiB + Life 프로세스 512MiB + 여유 512MiB.
Life 힙 256MiB를 계획하면, 장기 데이터 목표 128MiB 중 기록 약 61MiB,
다른 보드/UI/통계 공간 약 64MiB를 배정할 수 있다. 나머지 힙은 임시 객체/GC 여유.
통계 포함 보수적 704바이트/세대 가정에서는 기록 약 67.14MiB가 되므로
다른 장기 객체 예산을 약 60MiB 이하로 잡거나 128MiB 목표를 재조정해야 한다.
이 예산은 보증된 OS 사용량이 아닌 설계 가정이다. 다른 팀 기능 추가 시 다시 측정한다.
-Xmx는 힙만 제한하며 전체 프로세스 사용량을 제한하지 않는다. 실행 스크립트에는 강제하지 않았다.
