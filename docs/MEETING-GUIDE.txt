오늘 회의 준비 — 반복 감지와 세대 되돌리기

소개할 핵심
"기존 Cell.Memento 인터페이스를 이용해 세대별 보드를 저장하고 선택한 상태로 복원합니다.
이번에는 격자 전체가 과거와 같아지는 반복을 감지해 중복 저장을 멈췄습니다.
현재 세대 번호와 마지막 저장 세대를 분리했기 때문에 저장 범위는 고정되어도
Blinker처럼 상태가 바뀌는 동안 실제 세대와 보드 변화는 계속 진행됩니다.
다음 상태가 현재와 완전히 같으면 세대 번호를 늘리지 않고 안정 상태로 자동 정지합니다.
사용자 한도 설정은 없애고 1000개로 고정했으며, 비트 기반 상태로 저장 비용을 줄였습니다."

시연 순서 (실제 창에서 사전 확인 필요)
1. Grid > Load로 examples/blinker.life를 불러온다. 0세대/저장 1개.
2. +1세대: 현재 1, 저장 범위 0~1, 가로/세로 방향 변화.
3. +1세대: 현재 2, 저장 범위는 0~1 유지, 주기 2/반복 감지 표시.
4. 실행 후 정지: 현재 번호만 증가하며 보드 애니메이션은 계속되는지 확인.
5. 최신을 눌러 저장된 1세대로 돌아가기. 번호 0 입력/슬라이더로 왕복 탐색.
6. 저장 세대에서 셀을 하나 수정해 반복 감지가 초기화되는지 확인.
7. glider.life를 불러와 20세대 이상 진행: 이동하므로 새 상태가 계속 저장됨을 확인.
8. boundary-blinker.life로 경계 복원 후 계산이 같은지 확인.
9. 빈 보드나 고정 블록에서 실행/+1세대를 눌러도 번호가 증가하지 않음을 확인한다.
10. 0~20세대를 만든 뒤 10세대로 이동해 편집: 저장 끝이 즉시 10으로 줄고,
    +1세대로 새 11세대 기록이 생성되는지 확인한다.
11. 편집한 10세대에서 25세대까지 진행 후 9세대로 돌아가 +1세대:
    편집한 셀이 복원되고 11~25세대 기록도 보존되는지 확인한다.
12. sh test.sh의 153개 통과 결과를 보여 준다. 종합 검증 내역은 AUDIT-REPORT.txt 참고.

결정 근거
- Life의 이전 상태는 현재 상태만으로 일반적으로 유일하게 역계산할 수 없어 상태 저장 필요.
- 반복은 일부 영역이나 생존 셀 수가 아닌 전체 격자의 같은 좌표 상태를 비교.
- 반복을 감지하기 전까지 긴 비반복 구간이 있을 수 있으므로 보관 한도 자체는 유지.
- 설정 UI는 제거하고 1000개 고정: 64×64 보드에서 셀 비트 데이터 약 500KiB.
- 보관 상태를 매번 전체 직렬화하지 않고 BitSet Memento로 비교/복원.
- 최근 보관 목록은 첫 재등장을 즉시 감지하고,
  보관 한도보다 긴 주기는 Brent 감지기로 보완(기준 상태 한 개 추가).
- 편집으로 새 계산을 시작하면 해당 시점 이후 상태끼리만 반복을 비교한다.
  수동 편집 이전 기록과 같다는 사실은 새 실행의 주기성을 보장하지 않기 때문이다.
  기존에는 이동 중인 Glider를 과거 위치로 편집하면 반복으로 오인해 저장이 중단됐다.
  이 경우의 실패를 재현한 후 비교 범위를 제한해 수정했다.
- 긴 주기 탐지는 첫 재등장 시점보다 늦을 수 있다. 감지 시점 직전까지의 저장을 보존.
- 반복 후 저장 범위 밖 현재 번호에서 편집하면 해당 번호로 새 연속 기록 구간을 시작.
  저장되지 않은 번호를 기록이 있는 것처럼 보여 주지 않기 위한 정책이다.

자료 구조 / 호출 흐름
Clock 또는 +1세대 → LifeHistory.advance
  다음 저장 세대 존재: 해당 상태 복원, 미래 기록 유지 (편집 내용도 그대로 재생)
  저장 끝 도달: Cell의 다음 상태 계산
  변화 없음: 안정 상태 표시 → 번호/기록 유지 → UI 변경 리스너에서 Clock 정지
  변화 있음: transition → 실제 generation 증가
  반복 미감지: BoardSnapshot.capture → 최근 기록/긴 주기 비교 → 반복이면 저장 중단
  주기 2 이상 반복 감지 후: 추가 스냅샷 캡처/비교 없이 보드 계산과 번호 증가 계속
탐색 → 정지 → history.seek → clear/transfer(LOAD) → 기존 감지 결과 보존 → 표시 갱신
편집 → 정지 → 보드 변경 → boardEdited → 분기/새 구간 및 감지 초기화

패턴 설명
원본에 있던 Memento를 재사용/확장했다. BoardSnapshot은 메모리 내 상태 표현을 맡고,
기존 파일 Memento는 .life 형식을 유지한다. 히스토리가 Caretaker 역할이다.
LifeHistory의 변경 알림은 Observer 방식이다. 전체 원본 설계 리팩터링을 완료한 것은 아니다.

통합 계약
- 원본 기준 커밋 1b9559e, Java 17 대상 컴파일. 현재 검증 실행은 JDK 26.
- Universe/Clock/Life는 충돌 가능성이 높은 공통 파일. 클래스 전체 덮어쓰기 금지.
- 세대 계산은 Clock → LifeHistory.advance 경로에서 한 번만 수행.
- 랜덤 생성/패턴 삽입/편집: Clock.stop → 변경 → history.boardEdited를 EDT에서 호출.
- 새 게임/Load: 성공한 변경 후 history.reset.
- 규칙/경계 조건/보드 크기를 바꾸면 현재 반복 판정의 전제가 달라지므로 새 기록 시작.
- 새로운 상태 속성(셀 나이/색상 등)이 게임 결과에 영향을 준다면 BoardSnapshot의
  저장/동등성 비교에도 포함해야 한다. 현 구현은 원본의 생존/죽음과 보드 폭을 저장한다.
- 미래 설계 개선 후보: Universe 책임 분리, 공통 보드 변경 이벤트, Snapshot 인터페이스.

검증 범위
실제 Conway 보드로 Blinker, 정지 블록, 빈 보드, transient 소멸 후 반복,
Glider+Blinker 혼합, 복원 후 계산, 원본 파일 왕복을 검사했다.
긴 주기/보관 한도 검사는 합성 결정적 보드로 기간 1009와 10000을 검사했다.
Brent 탐지기의 여러 주기/비반복 앞부분도 별도 검사했다.
UI 연결과 실제 Swing 타이머 실행/정지/재시작을 headless 환경에서 검사했다.
네이티브 메뉴/창/파일 선택기의 실제 화면 시연은 미검증이다.

성능 측정
64×64, 30% 밀도의 고정 난수 보드 4개에서 각각 1800세대 진행.
동일 보드를 200개/1000개 설정으로 비교했으며 실제로 1000개를 채우는 구간을 포함했다.
1000개가 찬 상태의 계산+캡처+비교+타임라인 갱신 322회:
중앙값 0.091ms, 95백분위 0.103ms, 최대 0.121ms.
전체 오프스크린 보드+패널 그리기 720회(10세대마다 표본):
중앙값 2.574ms, 95백분위 2.796ms, 최대 4.484ms.
UI는 Swing 이벤트 스레드에서 검사했으나 실제 OS 창/입력/합성/타이머 스케줄링은 미검증.
특정 컴퓨터의 관찰값이며 모든 환경의 응답 속도를 보장하지 않는다.
객체 오버헤드/전체 JVM 메모리는 셀 데이터 500KiB 수치에 포함하지 않았다.
세부 비교: performance-check.txt

GitHub 반영
로컬 feature/generation-timeline에 변경만 작성했으며 커밋/push하지 않았다.
검토 후 git add와 실제 커밋을 만들고 개인 기능 브랜치로 push한다.
함께 제공한 generation-timeline.patch는 원본 기준 커밋 대비 누적 패치다.
이전 버전 패치가 이미 적용된 곳에 중복 적용하지 말고 최신 소스 변경을 비교할 것.
lib/와 build/는 Git 제외. 오프라인 테스트에는 ZIP의 lib/를 복사하거나 Maven을 사용.
